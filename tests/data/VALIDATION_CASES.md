# Кейсы валидации прототипа Semantic TextNavigator

Автономный E2E-набор на Playwright, проверяющий прототип «проверка условий
договоров поставки» на соответствие тестовому заданию. Кейсы не зависят от
вёрстки: все утверждения строятся по нормализованному тексту страницы
(любые пробелы/кавычки/регистр унифицируются), поэтому набор применим к любой
реализации ТЗ.

- Дата проверки по сценарию: **10.03.2026**.
- Эталон и ловушки описаны в `../validation_checklist.md`.
- Каждый кейс `TC-XX` в отчёте помечен требованиями ТЗ в квадратных скобках
  (`A` — эталонные ответы, `B1..B10` — функциональные, `C1..C4` — технические,
  `Q1..Q4` — вопросы пользователя).

## Как запускать

```bash
# 1) установить зависимости (один раз)
npm install -D @playwright/test
npx playwright install chromium

# 2) сгенерировать фикстуры из эталонной папки uploads/
python3 make_fixtures.py ../uploads

# 3a) запуск в этой песочнице (надёжный standalone-runner, см. ниже «Про runner»)
APP_URL=http://127.0.0.1:8000 node run_e2e.js

# 3b) ИЛИ обычный runner на машине с ≥2 ГБ ОЗУ
APP_URL=http://127.0.0.1:8000 npx playwright test
```

`APP_URL` — адрес проверяемого приложения (по умолчанию `http://127.0.0.1:8000`).

## Про runner и память

В этой песочнице cgroup ограничен ~1 ГБ ОЗУ. Дерево процессов `npx playwright test`
(runner + worker + браузер) приводит к мгновенному OOM-крашу рендерера
(`Target crashed`). Библиотека Playwright, запущенная одним процессом, работает
стабильно, поэтому добавлен `run_e2e.js` — лёгкий runner, который перехватывает
`require('@playwright/test')`, подставляет шим (`test`/`expect`/`describe`/
`beforeAll`/`afterAll`) и выполняет **те же самые `.spec.js`** одним браузером.
Сами spec-файлы при этом остаются валидным артефактом для обычного
`npx playwright test` на машине интервьюера.

## Фикстуры (`make_fixtures.py`)

Генерируются из эталонной папки, ничего не зашито вручную:

- `original` — 6 исходных документов (эталон).
- `mut_amount` — изменено одно поле: сумма в подписанном ДС №1.
- `new_contract` — + новый договор STN-201 того же общего формата и ДС к нему.
- `no_amendment` — комплект без подписанного ДС №1.
- `future_amend` — ДС №1 вступает в силу после даты проверки.
- `conflict` — два конфликтующих подписанных ДС к STN-102.

## Негативный контроль (доказательство, что тесты «не слепые»)

`../reference_app/sabotage_server.py` — намеренно неправильный сервер: зашивает
сумму STN-101 = 1 380 000 (нарушение C1). Прогон набора против него **обязан**
уронить TC-11, TC-13, TC-14 (те, что требуют пересчёта из входных документов).
Проверено: 12 passed / 3 failed — именно эти три. Значит набор реально ловит
зашитые ответы.

```bash
cd ../reference_app && python3 sabotage_server.py 8001 &
cd ../validator && APP_URL=http://127.0.0.1:8001 node run_e2e.js
```

## Что покрыть вручную (не автоматизировано)

- D1–D5 (README, продуктовая записка, архитектура, отчёт о вайбкодинге, секреты) —
  проверяются просмотром репозитория, см. `../validation_checklist.md`.
- Визуальное удобство «перехода к абзацу» (подсветка/скролл) — кейсы проверяют
  наличие файла и точной цитаты, но не пиксельную подсветку.
- Скорость и поведение на больших объёмах (100 000 документов) — вне рамок E2E.
