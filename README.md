# Проверка условий договоров поставки — прототип

**Тестовое задание на позицию Product Owner (Semantic TextNavigator).**
Веб-приложение для закупщика: загрузил TXT-документы → получил таблицу условий
договоров (номер, поставщик, сумма, срок поставки) **на заданную дату проверки**,
где каждое значение подтверждается точной цитатой из исходного документа с
переходом к абзацу. Подписанные допсоглашения применяются; проекты и письма
показываются отдельно как несогласованные предложения; при отсутствии сведений —
«нет данных», при сомнении — «требует проверки».

---

## 1. Быстрый старт

Зависимости: **Python 3.10+ и ничего больше** (только стандартная библиотека).
Платные API и подписки не используются, LLM внутри нет (обоснование — §6).

```bash
cd contract-checker
python3 run.py                       # http://127.0.0.1:8000
# сеть/контейнер: python3 run.py --host 0.0.0.0 --port 8000
```

Тесты (79 шт., ~1 с):

```bash
python3 -m unittest discover -v
```

### Пример использования (демо-сценарий)

1. Открыть http://127.0.0.1:8000, нажать **«Загрузить учебные документы»**
   (6 TXT из папки `documents/`) — или перетащить свои файлы в зону загрузки.
2. Дата проверки по умолчанию **10.03.2026** (меняется в шапке). Нажать
   **«Проанализировать»**.
3. Таблица «Условия договоров»: клик по сумме/сроку раскрывает **цепочку
   оснований** (договор → допсоглашение), у каждого шага — файл, пункт, точная
   цитата и кнопка **«показать в тексте»** (документ с подсветкой и прокруткой
   к абзацу).
4. Раздел «Несогласованные предложения» — проект допсоглашения и письмо
   поставщика: значения, которые **не действуют**, но требуют реакции закупщика.
5. Раздел «Вопросы закупщика» — четыре вопроса из задания (В1–В4) с настраиваемыми
   параметрами (договор, пороговая дата).

## 2. Записка о решении

### Для какого пользователя
Специалист по закупкам, который ведёт десятки договоров поставки и тратит часы на
перечитывание документов и допсоглашений, чтобы ответить на простые вопросы
«какая сумма и срок действуют сегодня». Ценность: ответ за секунды **и**
юридически проверяемое основание к каждому значению (файл, пункт, цитата), а не
«доверься машине». Пользователь работает в режиме сверки и контроля, система не
принимает решений за него.

### Пять вопросов клиенту перед развитием
1. **Шаблоны.** Насколько стандартизованы документы? Сколько реальных шаблонов
   договоров/допсоглашений/писем нужно покрыть, и кто владеет их формами?
2. **Источник истины о подписании.** Есть ли ЭДО (Диадок и т.п.) с машиночитаемой
   подписью, или статус — только текстовая строка «подписано обеими сторонами»?
3. **Конфликты и приоритеты.** Как поступать при нескольких подписанных
   соглашениях с одной датой вступления в силу, при противоречащих правках одного
   пункта, при «рамка + спецификации»?
4. **Интеграции.** Куда должен попадать результат: ERP/1С, календарь поставок,
   уведомления о несогласованных предложениях и приближающихся сроках?
5. **Доступы и аудит.** Кто какие договоры видит (филиалы/поставщики/суммы),
   нужен ли аудит-лог обращений к документам, есть ли коммерческая тайна в суммах?

### Принятые допущения
- Маркер подписания — строка «Статус: …подписан(о) обеими сторонами…» (или явное
  «не подписан»/«проект»); отрицание проверяется раньше положительной формы.
  Статус не определён → изменения не применяются + «требует проверки».
- Подписанное соглашение без явной даты вступления в силу действует **с даты
  подписания** (аналог п. 1 ст. 425 ГК РФ); допущение показывается
  предупреждением. Дата вступления в силу после даты проверки → изменение
  «подписано, но ещё не действует» (pending), не применяется.
- Сумма договора = «общая стоимость поставки составляет X рублей»; авансы
  («входит в общую стоимость») и внутренние лимиты бюджета суммой не являются.
- Срок поставки = «поставить … не позднее ДАТЫ» (или «до даты»); сроки оплаты и
  приёмки сроком поставки не считаются.
- Документ связывается с договором по номеру договора в его тексте; имя файла и
  дата загрузки приоритета не дают. Письмо связывается с первым упомянутым
  договором.
- Формат входа — TXT (UTF-8, авто-fallback на windows-1251). OCR, PDF/DOCX —
  вне объёма (оговорено заданием).
- Дата проверки — параметр пользователя (по умолчанию в UI выставлена 10.03.2026
  из задания; серверный дефолт — сегодня).

### Две метрики полезности/качества
1. **Точность извлечения (Precision/Recall) по золотому набору.** Сейчас: 6/6
   документов классифицированы верно, 8/8 значений полей верны, статусы
   (changed / no_data / proposal) — верно, что закреплено автотестами. Цель при
   росте: Precision ≥ 97 % на 50–100 реальных документах при доле
   «требует проверки» ≤ 5 % (лучше честный needs_review, чем тихая ошибка).
2. **Проверяемость оснований = 100 %.** Каждое непустое значение имеет цитату,
   для которой автоматически выполняется `quote == text[char_start:char_end]`
   (сквозной тест по всем доказательствам результата). Обратная сторона метрики —
   0 выдуманных значений: значение либо подтверждено цитатой, либо «нет данных».
   (Кандидатом в третью метрику беру время закупщика «загрузка → ответ на вопрос»,
   целевое < 30 с.)

### Архитектура (схема)

```
 TXT-файлы (drag&drop)                     веб-интерфейс (vanilla JS)
        │  base64/JSON                       ▲  таблица │ цепочки оснований │ вопросы
        ▼                                    │  просмотрщик с подсветкой цитаты
 ┌────────────────────── HTTP (stdlib) ──────┴───────────────────────────┐
 │ app/server.py   POST /api/analyze · POST /api/question · static       │
 └───────┬───────────────────────────────────────────────┬───────────────┘
         ▼                                               ▼
 app/documents.py  классификация + реквизиты     app/questions.py  4 вопроса
 (тип/статус/номера/даты/связи)                  (параметризуемые шаблоны)
         ▼                                               ▲
 app/extraction.py  РЕЕСТР ПОЛЕЙ FieldSpec               │
 (regex-правила → значение + Evidence{файл,пункт,        │
  цитата,offsets,строка})                                │
         ▼                                               │
 app/resolution.py  разрешение «на дату»: signed&effective│
 допсоглашения → история значения; проекты/письма →       │
 proposals; неясности → warnings/needs_review ───────────┘
```

Ядро — чистый Python без I/O: `analyze(files, as_of) -> AnalysisResult`.
Транспорт (HTTP) и UI — тонкие слои. `app/models.py` — контракты данных
(Evidence, ValueStep, FieldValue, Proposal, ContractView).

### Три ключевых технических решения и компромиссы
1. **Детерминированные правила (regex по устойчивым формулировкам) вместо LLM.**
   *Плюсы:* воспроизводимость, точные offsets цитат «бесплатно», честное
   «нет данных», работа офлайн без ключей и денег, скорость. *Минусы:* хрупкость
   к новым шаблонам — каждый незнакомый оборот требует нового правила. Компенсация:
   нераспознанное не угадывается, а подсвечивается как «требует проверки»;
   добавление правила — декларация `FieldSpec` в одном файле. Масштабирование —
   гибрид «LLM как генератор гипотез + substring-валидация цитат» (§6).
2. **Реестр полей (FieldSpec) как точка расширения.** Поля (сумма, срок) описаны
   декларативно: позитивные/негативные паттерны, правила для предложений, парсер.
   Колонки таблицы и сериализация строятся из реестра, поэтому добавление
   «ставки неустойки» — ~15 строк в `extraction.py`, без правок UI и API.
   *Минус:* общая абстракция чуть сложнее «двух хардкод-парсеров» — окупается
   на первом же новом поле.
3. **Доказательство (Evidence) — первоклассная структура данных.** Каждое
   значение хранит файл, пункт, точную цитату, символьные offsets и номер строки.
   Это даёт «переход к абзацу», машинную самопроверку в тестах и будущий
   аудит-трейс. *Минус:* больше данных в ответе и строгое требование: любой
   сдвиг текста инвалидирует offsets (в прототипе текст неизменяем после
   загрузки — риск снят; в проде offsets надо пересчитывать при версиях
   документа). Плюс сознательный выбор: **ноль зависимостей** (stdlib
   `http.server` + vanilla JS) — запускается где угодно одной командой; цена —
   нет async/ORM/персистентности, сессии в памяти процесса.

### Что изменится при 100 000 документов и наличии прав доступа
- **Хранение и конвейер:** вместо загрузки TXT в память — объектное хранилище
  (тексты) + Postgres (метаданные, извлечённые значения, ссылки на цитаты);
  парсинг в фоне при поступлении документа (воркеры/очереди), а не по кнопке.
- **Запросы:** таблица — это SQL-выборка по индексам (номер, контрагент, даты,
  статус) с пагинацией; «значение на дату» — materialized view / событие
  «вступило в силу» в логе изменений, пересчёт инкрементальный.
- **Поиск:** полнотекстовый индекс (Postgres FTS/ES) по цитатам и реквизитам —
  заодно основа семантического поиска продукта.
- **Права:** RBAC/ABAC на уровне договора и контрагента (row-level security),
  фильтрация до выдачи, аудит-лог доступа; ядро извлечения прав не знает —
  авторизация живёт в API-слое. Сессии вопросов → stateless (данные в БД).
- **Качество:** мониторинг доли needs_review и расхождений с эталоном,
  регрессионный golden-set при каждом изменении правил.

### Три следующих улучшения (по приоритету)
1. **Реальные форматы и подписание:** PDF/DOCX + проверка машиночитаемой подписи
   (ЭДО) вместо текстовой строки «Статус:» — сегодня это главный источник риска
   ложного доверия.
2. **Гибридный LLM-слой для нестандартных формулировок:** модель предлагает
   (поле, значение, фрагмент), система валидирует цитату substring-проверкой и
   показывает confidence; не прошло — «требует проверки». Снижает долю ручного
   разбора при сохранении проверяемости.
3. **Персистентность и проактивность:** хранение документов/истории проверок,
   уведомления («поставка через 3 дня», «несогласованное предложение висит
   N дней»), экспорт в ERP — переход от «справочника» к рабочему инструменту.

## 4. Известные ограничения и заглушки

- **Только TXT** (UTF-8 / windows-1251 fallback). PDF, DOCX, сканы/OCR — вне объёма.
- **Правила рассчитаны на устойчивые формулировки шаблона** («стоимость …
  составляет N рублей», «поставить … не позднее ДАТА», «пункт N изложить в
  редакции»). Нестандартный оборот → «нет данных» / «требует проверки»
  (никогда не выдуманное значение), но покрытие новых шаблонов требует
  добавления правил. Цитата расширяется до строки: перенос формулировки на
  несколько строк правилами не ловится.
- **Статус подписания — из текста.** В реальности нужен ЭДО/криптоподпись.
- **Сессии анализа в памяти процесса** (перезапуск сервера → перезагрузить
  документы). Single-user прототип: нет авторизации, логирования, БД.
- **Письмо связывается с одним договором** (первое упоминание номера).
- **Конфликты «два соглашения, одна дата вступления в силу»** разрешаются
  детерминированно (по дате документа и имени файла), но без юридического
  анализа приоритета — ситуация дополнительно не подсвечивается.
- Вопросы В1–В4 — фиксированный набор шаблонов с параметрами, не произвольный
  чат (по условию задания произвольный чат в объём не входит).
- LLM в приложении не используется — намеренно (§6); платные API не нужны.

## 6. Нужен ли здесь LLM? Обоснование подхода и границы

Для ядра задачи LLM **не нужен и вреден**: ключевые требования. Правила дают offsets цитаты по
построению и детерминированный результат; LLM потребовал бы отдельного слоя
верификации (его «цитаты» надо обратно искать в тексте), недетерминирован.
Документы полуструктурированы — это зона правил.

Границы: при разнородных шаблонах, свободных формулировках писем, многоязычии и
OCR-шуме правила деградируют в «нет данных/требует проверки». Правильное
масштабирование — **гибрид**: LLM как генератор гипотез (поле, значение,
фрагмент), правила как валидатор (substring-проверка цитаты по offsets,
форматный парсер значения, порог уверенности). Не прошло валидацию → статус
«требует проверки». Так семантика расширяет покрытие, а проверяемость и
«ноль выдумок» сохраняются. Архитектура прототипа к этому готова: гипотезы
можно подавать в те же `Evidence`/`FieldValue`, не меняя контрактов модулей.

## 7. Отчёт о вайбкодинге

**Инструмент.** Qwen — AI-агент с песочницей: генерация кода, запуск тестов и
сервера прямо в рабочей папке. После генерации первой версии перенес проект в VS Code и дальше работал в Cline.
Первая версия потребовала корректировки блока вопросов, так как дублировался вопрос о сумме договора.
Большая часть времени ушла на валидацию результата и прогоны тестов, всего около 2 часов.

**Способ проверки результата (сквозной).** Каждый прогон: 79 автотест, покрывающих основные тест-кейсы. 
UI: jsdom-смоук (логика, 42 проверки), отдельное скрипты проверяющие работу прототипа в браузере через Playwright (отдельный проект) и обязательная ручная проверка в реальном браузере.

**Оставшиеся задачи (не сделано сознательно):**
- Персистентность, авторизация, PDF/DOCX, LLM-гибрид — описаны в §2
  («100 000 документов», «три улучшения»), вне рамок 4 часов.
- UX-полировка (сортировка таблицы, экспорт в CSV, мобильная вёрстка).
